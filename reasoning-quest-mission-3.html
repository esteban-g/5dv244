The Clingo Solver

🔎 Mission Briefing

Consider the following ASP program:

bird(tweety).
bird(polly).
penguin(polly).

flies(X) :- bird(X), not penguin(X).

Your first task is to determine what the solver should conclude.

Which answer set is correct?

🧩 The Solver's Reasoning

Now let's slow the reasoning down.

The solver sees:

bird(tweety).
bird(polly).
penguin(polly).

flies(X) :- bird(X), not penguin(X).

For tweety:

  • bird(tweety) is true.
  • penguin(tweety) cannot be derived.
  • Therefore not penguin(tweety) succeeds.
  • So flies(tweety) is derived.

For polly:

  • bird(polly) is true.
  • penguin(polly) is explicitly true.
  • Therefore not penguin(polly) fails.
  • So flies(polly) is not derived.
What role does not play here?

💻 Debug the Knowledge Base

A researcher gives you the following ASP program. Something is wrong with the intended reasoning.

bird(tweety).
penguin(tweety).

flies(X) :- bird(X), not penguin(X).

The researcher claims:

"Tweety is a bird, therefore Tweety flies."

Is this conclusion supported by the ASP program?

🧠 Predict Before You Solve

One of the most useful skills when working with ASP is learning to predict what the solver should produce before running the program.

Consider:

student(alice).
student(bob).

studies(alice).

prepared(X) :- student(X), studies(X).

Which atom should be derived?

🎓 Mission Reflection

You have now moved from reading ASP rules to reasoning about what an ASP solver will derive.

Three ideas are particularly important:

  • Facts describe what is explicitly known.
  • Rules describe how additional knowledge can be derived.
  • Negation as failure means that a literal cannot currently be established from the knowledge base.
